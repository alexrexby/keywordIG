## Б1. `panel.py:485-495` + `meta.py:237-238` — вердикт №1 после КАЖДОГО рестарта врёт и вытесняет оба самых важных `down`

Состояние канала алертов (`last_alert_ok_at`, `last_alert_error`) живёт в памяти процесса.
Рестарт — деплой, `docker compose up -d`, перезагрузка хоста, собственный SIGTERM сторожка —
обнуляет его. Вердикт 1.4 при этом стоит ВЫШЕ, чем 1.9 («слушает другой аккаунт») и 1.10
(«не пришло ни одного уведомления»), которые план §3.3 называет главными для установщика.

Прогон (тот же контейнер, только `docker restart`):

| до рестарта | после рестарта |
|---|---|
| `[down] Алерты не доходят — Telegram ответил 401: Unauthorized` | `[warn] Канал алертов не проверен` |
| строка «Уведомления: не приходили ни разу» (down) — под вердиктом | она же, под вердиктом |

То есть на свежей установке и после каждого деплоя человек читает **warn поверх down**, а текст
вердикта утверждает факт, который неверен: «ни одно сообщение по ним ещё не уходило» — уходило,
минуту назад, и получило 401. Симметрично: реально сломанный канал понижается с точной причины
(«Telegram ответил 401») до «не проверен ни разу» и остаётся таким, пока что-нибудь не попробует
отправить алерт.

Это тот же класс, ради которого `ever_received` героически спрашивают у последовательности
(чтобы пережить чистку) — но соседнее поле того же экрана живёт в памяти.

Минимальный диф: хранить состояние канала в базе, как токен. Одна строка вида

```sql
-- миграция 006
CREATE TABLE instagram.ig_alert_channel (
  id           int PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  last_ok_at   timestamptz,
  last_error   text,
  updated_at   timestamptz NOT NULL DEFAULT now()
);
```

`meta.alert_owner` пишет туда исход (это не write-транзакция через сеть: запись ПОСЛЕ ответа
Telegram, соединение берётся отдельно), `admin.state` читает. Если писать в БД из `meta` не
хочется — минимум переставить 1.3–1.5 НИЖЕ 1.9 и 1.10 и переписать текст на «с последнего
запуска сервиса сигналов не отправлялось», чтобы вердикт не утверждал того, чего не знает.

## Б2. `panel.py:586-600` + `618-644` — полная тишина дольше срока хранения журнала читается как «Сервис отвечает» (зелёный)

`_days_since(None)` возвращает `None`, вердикт 1.11 пропускается, и мы падаем в 1.12. А
`last_at = NULL` при `ever_received = true` — это не экзотика, это ровно то, что получается,
когда подписка отвалилась и прошло больше `EVENT_RETENTION_DAYS` (30 суток по умолчанию):
журнал вычищен, признак «когда-либо» жив.

Прогон `_verdict` на `{"ever_received": True, "kept": 0, "last_at": None}`:

```
[ok] Сервис отвечает
    За сутки разобрано 4 уведомлений, отправлено 3 сообщений. Очередь пуста.
summary: Уведомления=последнее никогда, в журнале 0 (ok)
```

Зелёная карточка и зелёная строка «последнее никогда». Установка, которая молчит дольше всех,
выглядит здоровее всех — а это ровно тот случай, который §3.3 называет самым дорогим
(«тишина здесь выглядит точно так же, как исправная работа в выходной день»).

Минимальный диф — в `_verdict`, перед `silent = _days_since(...)`:

```python
    silent = _days_since(hooks["last_at"])
    if hooks["ever_received"] and hooks["last_at"] is None:
        # Журнал вычищен ретеншеном, а нового не приходило: тишина ДОЛЬШЕ EVENT_RETENTION_DAYS.
        silent = EVENT_RETENTION_DAYS
```

и в `_summary` — уровень `warn`/`down` для строки «последнее никогда, в журнале 0», а не `ok`.

## Б3. `panel.py:803-824` + `admin.save_rule` — «Выключить» не работает у правила, чьи ХРАНИМЫЕ поля не проходят текущую валидацию

`rule_toggle` ходит тем же `save_rule`, а тот прогоняет `_prepare` по ВСЕМ полям, слитым из
`current`. Значит выключение проверяется теми же правилами, что включение.

Прогон на живой базе (правило 1 из `003_seed_rule.sql`, вручную переведено в `enabled = true`,
кнопка со ссылкой на кириллице — так она и лежит в поставке):

```
POST /panel/rules/1/enabled  enabled=0  ->  400
   «Правило не сохранено — кнопка 1: ссылка должна начинаться с https:// и быть латиницей»
в БД после попытки: enabled = t
```

То есть включённое правило, которое отвечает людям, **нельзя выключить из панели вообще**.
В машинном API то же самое (`PATCH {"enabled": false}` → 400 с той же причиной) — дефект
не этапа 3, он приехал из этапа 2. Но именно этап 3 делает панель ЕДИНСТВЕННЫМ человеческим
органом управления и рисует большую кнопку «Выключить»; для пакета, который развернёт посторонний,
это аварийный стоп, который не срабатывает. Триггеры реальны: правка правила SQL-ом, ужесточение
проверок в следующей версии пакета (`MAX_BUTTON_TITLE`, набор допустимых URL), ссылка, законная
для Meta, но не для нашего валидатора.

Минимальный диф — выключение не может сделать хуже, поэтому содержимое для него не проверяется:

```python
# admin.save_rule, в начале
    turning_off = set(body) == {"enabled"} and body["enabled"] is False
    values, errors, warnings = _prepare(
        body, current=current, siblings=await _siblings(body, current),
        rule_id=current["id"] if current else None,
    )
    if errors and not turning_off:
        return None, errors, []
    if turning_off:
        values, errors, warnings = {**current, "enabled": False}, [], []
```

(проверки на ВКЛЮЧЕНИЕ оставить как есть — там они и нужны).

# СРЕДНИЕ

## С1. `db.py:451-470` — ответ на вопрос №3: прав на последовательность бояться не надо, бояться надо ХРУПКОСТИ САМОЙ ПРОБЫ

Проверено на живом Postgres 16, тремя прогонами:

| что делал | результат |
|---|---|
| роль-владелец (как на установке: `CREATE SCHEMA … AUTHORIZATION ig_service`, миграции под ней) | работает, `ever_received` корректно |
| роль с `GRANT SELECT,INSERT,UPDATE,DELETE ON ALL TABLES`, без прав на последовательность | `pg_sequence_last_value` → `ERROR: permission denied for sequence`… |
| …но ей же `INSERT` в `ig_event` | **`ERROR: permission denied for sequence`** — вставка не работает тоже |

То есть страх «у установщика роль без прав на последовательность» опровергается: такая роль не
может и принять ни одного вебхука, отказ будет громким и на первом же событии, задолго до панели.
Прав на `bigserial` без прав на последовательность не бывает. **Отдельной находки здесь нет.**

Две настоящие проблемы рядом:

1. **Отказ пробы убивает ВЕСЬ `/ig/admin/state`, а не одно поле.** Проверено (`REVOKE ALL ON
   SEQUENCE … FROM ig_service`): `/panel/` → 500, `/ig/admin/state` → 500 (то есть и `doctor.sh`
   слепнет), `/panel/queue` при этом → 200. Одно необязательное поле уносит всю диагностическую
   поверхность. Минимальный диф — отдельный запрос и деградация:

   ```python
   async def event_stats() -> dict:
       async with pool_ref().connection() as conn:
           async with conn.cursor(row_factory=dict_row) as cur:
               await cur.execute("SELECT count(*) AS kept, max(received_at) AS last_at"
                                 "  FROM instagram.ig_event")
               row = await cur.fetchone()
           try:
               cur2 = await conn.execute(
                   "SELECT pg_sequence_last_value('instagram.ig_event_id_seq') IS NOT NULL")
               row["ever_received"] = (await cur2.fetchone())[0]
           except psycopg.Error:
               # Проба недоступна — это «не знаю», а не «не приходило»: вердикт
               # «не пришло ни одного уведомления» отправит человека чинить исправное.
               log.warning("проба последовательности недоступна — ever_received неизвестен")
               row["ever_received"] = row["kept"] > 0 or row["last_at"] is not None
       return row
   ```

   (и `conn.rollback()`/отдельное соединение, если проба идёт в той же транзакции: неудачный
   запрос аварирует транзакцию целиком, и следующий в ней получит `InFailedSqlTransaction` —
   порядок «сначала счётчики, потом проба» это уже закрывает, но проверьте прогоном).

2. **`TRUNCATE … RESTART IDENTITY` возвращает признак в `false`.** Проверено:
   `truncate instagram.ig_event restart identity` → `ever_received = f`. `DELETE FROM` — не
   возвращает (проверено, остаётся `t`), и это правильно. Но «почистить тестовые данные перед
   боевым запуском» человек сделает именно `TRUNCATE`, и панель после этого скажет «от Instagram
   не пришло ни одного уведомления» на работающей установке — то есть отправит проверять
   публикацию приложения Meta. Если хотите признак, который не зависит ни от прав, ни от
   `RESTART IDENTITY`, — это одна строка факта, а не проба последовательности:
   `INSERT INTO instagram.ig_fact(key, at) VALUES ('first_event', now()) ON CONFLICT DO NOTHING`
   рядом с `insert_events`. Дороже на один запрос при первом событии, дальше — `ON CONFLICT`.

# НИЗКИЕ

## Н1. `panel.py:111` — ответ на вопрос №5: дубль `STALE_SEC` лечится переносом в `config.py`, цикла не будет

`config.py` — лист: он не импортирует ни один модуль проекта, а `main.py` и `panel.py` оба
импортируют его уже сейчас. Значит порог переезжает туда без обратного импорта:

```python
# config.py
# Сколько секунд без круга диспетчера считаем смертью цикла. Читают трое: /ig/health (503),
# сторожок (SIGTERM себе) и панель (вердикт). Разъехавшись, они скажут про один круг разное.
HEALTH_STALE_SEC = _positive_int("IG_HEALTH_STALE_SEC", 120)
```

`main.py` и `panel.py` — `from config import HEALTH_STALE_SEC`, обе локальные константы и оба
комментария про «меняются вместе» уходят. Побочно порог становится настраиваемым, что полезно:
прошлое ревью (Т6) отмечало, что 120 с не связаны с темпом отправки.

## Н2. `panel.py:900-908` — повторное «Снять бронь» не говорит ничего

`_back(..., warnings=[...])` только пишет в лог и редиректит без `note`. Человек нажимает,
страница перезагружается, на экране — ничего. В машинном API тот же случай отдаёт 404 с текстом.
Минимально: код `no-hold` в `NOTES` («брони на этой доставке уже нет — снимать нечего»).

## Н3. `panel.py:249-262`, `265-289`, `304-311` — панель отвечает человеку JSON'ом

`require_open()` → 503 `{"detail": "Панель закрыта: не задан IG_ADMIN_SECRET …"}` (проверено),
`require_form` → 403 `{"detail": "Страница устарела …"}`, `read_form` → 413/415 тем же способом.
Всё это открывают в браузере. Текст правильный, оболочка — нет. Один обработчик `HTTPException`
для путей `/panel/*`, рисующий тот же текст шаблоном.

## Н4. `templates/token.html:11` — сырой ISO с микросекундами на странице для человека

`Автоответы стоят с 2026-08-26T20:27:40.010091+00:00` (проверено). Везде остальное время идёт
через `_when` («26.08.2026 20:27 UTC (только что)»). Передавать в шаблон уже отформатированное.

## Н5. `panel.py:340-352` — `hashlib.scrypt` блокирует event loop на 61,6 мс (замер в контейнере)

Замер: `check_password` → 61,6 мс. Замок (5 попыток / 300 с) делает это не DoS-вектором:
худший случай — 0,3 с блокировки на пять минут, приём вебхуков это переживёт. Отдельная находка
не нужна, но одна строка её закрывает совсем: `await asyncio.to_thread(hashlib.scrypt, …)`.
Заодно 16 МБ на проверку уходят из основного потока при `mem_limit: 256m`.

Про замок отдельно (объявленный дефект, разбор, а не повторный флаг): цена признана в
комментарии — «злоумышленник может держать владельца без входа пятиминутками». Проверено:
верный пароль во время замка тоже получает 429. Для инструмента, которым чинят аварию, это
дороже, чем кажется: снаружи `/panel/login` доступен по устройству, и пять POST'ов раз в
пять минут стоят атакующему ноль. Дешёвая альтернатива, не требующая IP: **сначала сверить
пароль, замок применять только к неудачам** — тогда владелец с верным паролем входит всегда,
а атакующий не получает ничего, кроме CPU; CPU ограничивается глобальным «не чаще одной
попытки в секунду» (одна переменная `time.monotonic()`). Считаю это строго лучше текущего
размена; решение за вами.

## Н6. `db.py:137-167` — ретеншен не трогает рабочие состояния, а политика обещает срок всем

`state NOT IN ('PENDING','CLAIMED','REPLIED_PUBLIC','SENT_DM')` — выбор перечислять рабочие,
а не терминальные, правильный и объяснён. Но заброшенная установка (токен умер, владелец не
чинит) копит `PENDING` с текстом обращения человека вечно, а `/privacy` пишет «храним
{{ retention_days }} суток, после чего сервис удаляет их сам». Расхождение маленькое и тихое.
Минимально — добавить в чистку строки, которые уже не отправятся ни при каких условиях:
`OR (state = 'PENDING' AND expires_at < now() - make_interval(days => %s))`.

## Н7. `templates/queue.html:6` — «Всё, что приходило, разобрано» на пустой таблице

`items` пуст ровно тогда, когда обращений НЕ БЫЛО ни одного (или все вычищены). Текст утверждает
факт о разобранной работе там, где работы не было. Мелочь, но это тот же класс «пустота выдаётся
за результат», за который здесь всё остальное сделано аккуратно. Развести две ветки по
`facts.webhooks.ever_received` или просто: «Обращений пока не было.»
